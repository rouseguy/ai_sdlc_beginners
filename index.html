About this document

Who this is for

This guide is for a junior developer. You choose the project. The agent writes most of the code. You make the decisions, and you check the result. Read the guide from start to end before you start.

What you learn

After you read this document, you can do these tasks:

  • Install and configure the tools.
  • Explain each phase of software development using coding agents.
  • Use the Matt Pocock skills and the Impeccable skill in the correct order.
  • Find the documents that the process writes, and know what each document controls.
  • Ask the agent how to deploy, which services the project needs, and where an API key goes.

Writing conventions

  • Bold text shows a name in a user interface or an important term.
  • Code font shows a command, a file name, or a value that you type.
  • A command that starts with / is a Claude Code slash command. You type it in the Claude Code prompt.
  • A command that starts with ! runs in the shell from the Claude Code prompt.

What software development using coding agents is

In ordinary software development, you write all the code. In software development using coding agents, an agent (Claude Code) writes most of the code. You still own the work. You do these tasks:

  • You choose the project and the decisions.
  • You give the agent clear context, in files.
  • You approve the actions that are risky or that you cannot easily undo.
  • You verify the result on real input.

The agent does the research, the writing, the coding, and the testing. You do not accept a result because the agent says it is done. You look at the evidence.

Skills give the agent a repeatable process. A skill is a packaged set of instructions for one type of task. One skill interviews you about a plan. Another skill turns that plan into tickets. You run the skills in order, on whatever project you choose.

The work has six phases:

flowchart LR
    A[1. Set up<br/>tools] --> B[2. Define<br/>the product]
    B --> C[3. Sharpen<br/>the idea]
    C --> D[4. Plan<br/>the work]
    D --> E[5. Build<br/>and test]
    E --> F[6. Deploy<br/>and verify]
    F -.->|feedback| C

Each phase writes documents in the repository. The next phase reads those documents. This is the most important rule: the repository holds the context, not the chat. A new session can continue the work because the decisions are in files.

Set up your workstation

You do these steps once on a new workstation.

Install the tools

  1. Install Claude Code and Orca.

  2. Open a terminal in Orca.

  3. Install Python, Node.js, and the GitHub CLI for your user account only:

    winget install -e --id Python.Python.3.12 --scope user
winget install -e --id OpenJS.NodeJS.LTS --scope user
winget install -e --id GitHub.cli --scope user

    Note: Use --scope user. A machine-wide install shows a Windows administrator prompt (UAC). The agent cannot accept that prompt for you. If you see a UAC prompt, you click Yes or No yourself.

  4. Install the Railway CLI:

    npm i -g @railway/cli

  5. Close the terminal and open a new one. This loads the new PATH.

  6. Make sure that each tool runs:

    python --version
node --version
gh --version
railway --version

Sign in to the services

  1. Sign in to GitHub:

    ! gh auth login

  2. Sign in to Railway:

    ! railway login

  3. Add the Railway MCP server to Claude Code:

    claude mcp add --transport http railway https://mcp.railway.com

  4. In Claude Code, type /mcp. Select railway, and then select Authenticate.

  5. Restart Claude Code with claude --continue.

    Important: Claude Code loads MCP tools only when a session starts. After you add or authenticate an MCP server, you restart the session. A restart also stops background agents and local servers. Wait until background work is complete before you restart.

Store secrets

A secret is a key that lets your app call an outside service. You never put a key in the chat, and you never commit a key.

  1. Ask the agent which service the project needs. For an app that parses a PDF, you can ask which service turns a PDF into fields, and what you must create on that service's website.

  2. Create the key on that website. Put it in .env.local at the root of the repository:

    PDF_API_KEY=<your key>

  3. Make sure that .gitignore excludes the file:

    git check-ignore -v .env.local

  4. When you deploy, add the same name as a Railway variable. The value stays in Railway. It does not go into the chat.

Warning: Do not paste an API key into the chat. Do not commit an API key. Locally, the key lives in .env.local. In production, it lives in a Railway variable.

The skills you use

Matt Pocock skills

The Matt Pocock skills are the engineering process. They move an idea to shipped code on a fixed path. The skills keep the decisions in the repository, so the next session can continue.

flowchart TD
    S[setup-matt-pocock-skills<br/>one time per repo] --> G[grill-with-docs<br/>interview + glossary + ADRs]
    G --> Q{Can you answer<br/>every question?}
    Q -->|No| P[prototype<br/>throwaway code]
    P --> G
    Q -->|Yes| SP[to-spec<br/>spec as GitHub issue]
    SP --> T[to-tickets<br/>vertical-slice tickets]
    T --> I[implement<br/>one ticket per session]
    I --> CR[code-review<br/>standards + spec]
    CR --> I
Skill What it does What it makes How you use it
/setup-matt-pocock-skills Configures the issue tracker, triage labels, and the location of domain documents. CLAUDE.md, docs/agents/*.md You choose GitHub Issues and the default labels.
/grill-with-docs Interviews you in rounds until the decisions are clear. It runs grilling and domain-modeling together. CONTEXT.md, docs/adr/*.md You answer each round. The decisions for your project land in files.
/grilling The interview engine. Each round asks every question that you can answer now, with a recommended answer. Decisions in the chat, then in files You do not type this yourself. grill-with-docs runs it.
/domain-modeling Keeps one name for each concept. Writes the glossary and the architecture decision records (ADRs). CONTEXT.md, ADRs You use the names from your project. You do not invent a second name for the same thing.
/to-spec Turns the conversation into a specification. A GitHub issue with user stories You run it after the interview. You read the issue before you approve it.
/to-tickets Splits the spec into tracer-bullet tickets. Each ticket cuts through every layer. Each ticket names what blocks it. GitHub issues with blocking links You approve the breakdown before any feature code is written.
/implement Builds one ticket test-first, then runs a code review. Code, tests, a commit You run one ticket per session. See Use the standard order.
/ask-matt Tells you which skill to use next. Advice You ask it when you are not sure of the next step.

Note: Some skills (/to-spec, /to-tickets, /implement) run only when you type them. The agent cannot start them. Type the full name, for example /mattpocock-skills:to-spec, as a message by itself.

Impeccable skill

The Impeccable skill is the design process. It keeps the interface honest. It does not start with colors and fonts. It starts with the product.

Command What it does What it makes How you use it
/impeccable init Interviews you about users, purpose, and constraints. It does not ask about visual style. PRODUCT.md You describe who the app is for, what it does, and what it must not do.
/impeccable (new work) Chooses a visual direction, builds the interface, and checks it against a craft floor. DESIGN.md, .impeccable/ You run it after PRODUCT.md exists, when a ticket needs a screen.
impeccable detect Scans the interface for known design problems. A report You run it before you call the interface finished.

Other commands, such as critique, audit, and polish, refine an interface that already exists. You use them after the first version works.

The workflow you follow

You follow these steps in order. The project can be anything you can describe in a few sentences. The examples below use an app that parses a PDF, so you can see how to ask. You replace that example with your own project.

flowchart TD
    A[Your idea] --> B[Configure skills<br/>CLAUDE.md]
    B --> C[Product context<br/>PRODUCT.md]
    C --> D[Grill the idea<br/>CONTEXT.md and ADRs]
    D --> E[Prototype<br/>the risky part]
    E --> F[Spec and tickets]
    F --> G[Build one ticket]
    G --> H[Run it on real input]
    H --> I[Deploy to Railway]
    I -.->|feedback| D

Step 1: Write a short brief

Goal: Say what you want to build, in one page.

You tell the agent the idea in plain language. You ask it to write docs/productbrief.md. The brief states the user, the outcome, what is out of scope, and the open questions.

For a PDF project, the whole brief can start from one sentence: "A person uploads a PDF and sees the fields the parser found."

Step 2: Configure the repository

Goal: Tell the skills where issues and domain documents live.

  1. Type /mattpocock-skills:setup-matt-pocock-skills.
  2. Answer the questions. You choose:
    • Issue tracker: GitHub.
    • Triage labels: the defaults.
    • Configuration file: CLAUDE.md.

Step 3: Capture the product context

Goal: Record the facts that do not change often.

  1. Type /impeccable:impeccable init.
  2. Answer the questions about the users, the purpose, and the name of your app.

The result is PRODUCT.md. Later design work reads this file.

Step 4: Sharpen the idea

Goal: Make the decisions before you write feature code.

  1. Type /mattpocock-skills:grill-with-docs and give a one-line scope. For the PDF example: "A small app. A person uploads a PDF and sees the parsed fields."
  2. Answer each round. Each question has a recommended answer. You accept it in one word, or you change it.
  3. Read each update to CONTEXT.md as the agent writes it.
  4. Accept the ADRs that the agent offers.

You answer these kinds of questions. The exact questions depend on your project:

Question What you decide Where it goes
Who is it for? The person who uses the app, and what they are trying to finish. PRODUCT.md
What is in, and what is out? The one outcome, and the things the first version does not do. PRODUCT.md, CONTEXT.md
What is the risky part? The piece you are not sure will work. For a PDF app, that piece is the parse. A short prototype
What do you store? What the app keeps, and what it throws away. An ADR
Which outside service? Which API does the hard work, and which key it needs. An ADR and .env.local
How does it ship? Railway, and which services (a web service, and a database only if you store data). An ADR

Tip: A decision can change before you commit it. You ask the agent to rewrite the ADR. After you commit an ADR, you add a new ADR that supersedes it. You do not silently edit the old one.

Step 5: Prototype the risky part

Goal: Prove the hard part with a throwaway script, before you design the whole app.

You ask for a small experiment, not a product. For the PDF example, you type:

Write a short script that sends one sample PDF to the parsing API and prints the fields. Do not build the website yet. Do not print the API key.

You run the script on a real file. You read the fields. If they are wrong, you change the decision now. A prototype is supposed to be thrown away.

Step 6: Write the spec and the tickets

Goal: Turn the decisions into work that someone else can track.

  1. Type /mattpocock-skills:to-spec. Read the user stories. Confirm how you will test the app: through the real interface, and with one real input.
  2. Type /mattpocock-skills:to-tickets. Read the breakdown. Approve it, or send it back.

Each ticket is a tracer bullet. It goes through every layer that the feature needs, and you can demonstrate it. Later tickets name the tickets that block them:

flowchart LR
    A[Walking skeleton] --> B[First real action]
    B --> C[Core feature]
    B --> D[Errors and empty states]
    C --> E[Deploy]
    D --> E

For an app that parses a PDF, the core feature is: upload a file and show the fields. You still use these slice names. You do not invent a different process for each project.

Step 7: Build one ticket at a time

Goal: Ship a thin slice that you can run.

You name one ticket, then you send this as its own message:

/mattpocock-skills:implement

The agent reads the ticket, CONTEXT.md, and the ADRs. It writes tests first. It shows you the test output. You approve the commit, or you send a correction.

You give a sub-agent a job only when the work splits into folders that do not touch the same files. You tell it the folder it owns, the folders it must not touch, the tests to write, and what to report. On a first project, one ticket at a time is enough.

Step 8: Run it on real input

Goal: Prove the slice on input that did not come from the tests.

  1. Run the tests.
  2. Start the app the way the ticket describes.
  3. Use one real input. For a PDF app, that input is a PDF you did not use while writing the tests.
  4. Compare the result with the file. If a value is not in the file, the app must not invent it.

Important: You run the real system on real input before you deploy. Tests with fakes cannot find the mistakes of a model or of an outside API.

Step 9: Deploy to Railway

Goal: Put the app on a public URL, with secrets kept out of the chat.

You do not memorize Railway's screens. You ask the agent, and you check its plan before it creates anything. For the PDF example, you type:

Deploy this project to Railway. It parses a PDF with an external API. Which Railway services does it need? How do I add the API key? Then deploy it. Do not print the key.
sequenceDiagram
    participant You
    participant Agent
    participant Railway
    You->>Agent: Which services?
    Agent->>You: Web service<br/>Database if needed
    You->>Agent: Add the key
    Agent->>Railway: Set the variable
    Railway-->>Agent: Public URL
    Agent-->>You: Open the URL
  1. Restart Claude Code so the Railway MCP tools load.
  2. Read the list of services. A web service is normal. A database is only for data you decided to store.
  3. Create the API key on the provider's website. Add it in Railway under the name from .env.local. You do this yourself, or you approve a tool call that sets the variable without showing you the value in the transcript.
  4. Approve the deploy.
  5. Open the public URL and try one real file. Check the values by hand.

Use the standard order

On a first project, you follow the skill order. You do not build the whole app and write the tickets afterwards.

flowchart LR
    A[grill-with-docs] --> B[prototype<br/>risky parts]
    B --> C[to-spec]
    C --> D[to-tickets]
    D --> E[implement<br/>ticket by ticket]
    E --> F[deploy]
  • You prototype the risky part. A late surprise is more expensive than a thrown-away script.
  • You write the spec, then the tickets, then you implement. The tickets drive the build.
  • You let implement run a code review for each ticket. You read the review.

Rules for working with the agent

Give context

  • You put decisions in files, not only in the chat.
  • You use the names from CONTEXT.md. You do not invent a second name for the same thing.
  • You give a sub-agent one task, one folder, and the documents to read.

Keep control

  • You approve every action that you cannot easily undo: commits, pushes, deploys, and deletions.
  • You accept a Windows UAC prompt yourself. The agent cannot see it.
  • You type the user-only skills yourself. The agent cannot start them.

Protect secrets

  • You keep keys in .env.local or in Railway variables.
  • You make sure that .gitignore excludes every .env* file before the first commit.
  • You do not paste a key into the chat. You ask the agent where the key goes, not to repeat the key.

Verify the result

  • You read the tests. A test checks behavior, not private details inside the code.
  • You run the real system on real input.
  • When the agent reports a result, you check the evidence: test output, the screen, and the logs.

Glossary

Term Definition
ADR Architecture decision record. A short file that records one decision and the reason for it.
Agent A program that reads files, runs commands, and writes code for you. In this guide, that program is Claude Code.
MCP Model Context Protocol. A standard way to give the agent tools for an outside service, such as Railway.
Skill A packaged set of instructions for one type of task.
Sub-agent A separate agent that the main agent starts for one task. It has its own context.
Tracer bullet A thin ticket that goes through every layer the feature needs, so that you can demonstrate it.
UAC User Account Control. The Windows prompt that asks for administrator permission.
Variable A named setting, such as an API key. Locally it lives in .env.local. In production it lives in Railway. It does not live in the chat.
